From: CEO (Arun)
To: Business Analyst Agent
Priority: P1 — real-usage UX gap in a feature built and deployed earlier tonight (B2B-39); blocks
resellers/admin from using their own regenerated passcode end-to-end on the demo tool they were just
given
Date: 2026-07-27

## What Arun Said

Relayed via the Orchestrator, direct follow-up on tonight's B2B-39 build (per-reseller demo passcodes
+ demo billing), same session:

"the passcode that saves name and meeting url is still old one and not using the new regenerated code.
can you fix that too?"

## The Problem Being Solved

Verified against live code before writing this brief, not assumed.

The `/demo/[slug]` demo tool has two passcode-gated actions on the same page, and after tonight's
B2B-39 build they now run on two different mechanisms:

- **`app/api/demo/[slug]/dispatch/route.ts`** (the "Learn with AI" bot-dispatch action) — **already
  correct**. Line 72: `const resolved = await resolveDemoPasscodeToAccount(parsed.data.passcode)`,
  imported from `lib/demo/passcode-accounts.ts` (line 5). This resolves the entered passcode to a
  specific `partner_accounts.id` per-account (`resolved.partnerAccountId`, used for billing
  attribution) and a `demo_passcodes.id` (`resolved.passcodeId`, written to the new `demo_dispatches`
  audit row at line 217 on a successful dispatch, per B2B-39 §6.9 point 4).
- **`app/api/demo/[slug]/meeting/route.ts`** (the "Save" action on the Meeting tab, persisting the
  meeting URL + participant name) — **still on the old mechanism**. Line 5:
  `import { verifyDemoPasscode } from '@/lib/demo/passcode'`; line 71:
  `if (!verifyDemoPasscode(parsed.data.passcode))`. This checks the entered string against exactly one
  shared secret, the `DEMO_MEETING_PASSCODE` env var (`lib/demo/passcode.ts` lines 22-25) — it has no
  notion of *which* account entered it, and does not recognize any passcode issued/regenerated by
  B2B-39's `demo_passcodes` mechanism.

This was a deliberate, documented scope decision at the time, not an oversight introduced by a bug.
`lib/demo/passcode-accounts.ts`'s own file header (lines 7-10) states: "that file's
[`lib/demo/passcode.ts`] `verifyDemoPasscode()` ... is completely untouched by this feature and must
never be merged with this mechanism (§10 Out of Scope — conflating the two would let a reseller's own
demo-billing passcode also unlock editing the meeting URL for every demo topic)." Its
`resolveDemoPasscodeToAccount()` doc-comment (lines 84-85) repeats this: "Used ONLY by the dispatch
route — never by the Meeting tab's Save action, which keeps using `lib/demo/passcode.ts`'s mechanism
unchanged."

In isolation that was a reasonable, deliberately conservative scoping call. Real usage tonight shows
it produces confusing operator UX: a reseller or admin generates/regenerates exactly **one** passcode
from their own dashboard card, and reasonably expects that same passcode to work for the whole demo
page — both saving the meeting details and dispatching the bot — not two different passcodes gating
two different buttons on the same screen, one of which (the shared `DEMO_MEETING_PASSCODE`) most
operators no longer even know since B2B-39 replaced it as their day-to-day credential.

## What Success Looks Like

`app/api/demo/[slug]/meeting/route.ts`'s POST (Save) handler resolves the entered passcode via
`resolveDemoPasscodeToAccount()`, exactly mirroring the dispatch route's own call — same function,
same import source. A passcode issued/regenerated for any `channel_partner` account or the admin
sentinel account now unlocks both actions on the demo page uniformly. Same visitor-facing error
shape/behavior on failure (401, `{ error: { code: 'incorrect_passcode', message: 'Incorrect
passcode.' } }`) — the dispatch route's own comment at lines 69-71 already establishes "same error
shape/code as before" as the right posture for a mechanism swap; this brief should follow the same
discipline.

**What the Save action needs from the resolved result — stated explicitly, per the brief's own
question:** gate-only. Saving a meeting URL and a participant name has no billing or attribution
consequence — only *dispatching* a bot (which burns demo minutes against a specific account) does.
`demo_meeting_urls` (migration `093_b2b33_demo_meeting_dispatch.sql`) has no `partner_account_id` or
any other account-identity column today, and its own table comment states plainly: "Not a
partner-facing table." The Save action therefore only needs `resolveDemoPasscodeToAccount()` to return
non-null (a valid, active, unrevoked passcode was entered) to allow the save to proceed — it does not
need to read, store, or forward `resolved.partnerAccountId` or `resolved.passcodeId` anywhere.
`demo_dispatches` (B2B-39, `supabase/migrations/100_b2b39_demo_passcodes_and_billing.sql`) already
captures billing attribution at the one point it actually matters — dispatch time — and its own table
comment states it is "written by `app/api/demo/[slug]/dispatch/route.ts` immediately after a
successful dispatch," not by the Save action.

### Design question 1 — does the GET handler need a passcode check?

Checked the actual current GET handler (`app/api/demo/[slug]/meeting/route.ts` lines 29-46), not
assumed: **no, and this brief does not change that.** The file's own header comment (lines 12-14)
already states the intended design plainly: "GET is unauthenticated (page-viewing-equivalent — the
'Currently saved' summary line and the Learn with AI button's enabled/disabled state both depend on
it)." The GET function has zero passcode logic of any kind — it looks up `getDemoTopicBySlug()`, then
reads `meeting_url`/`end_user_name`/`updated_at` straight from Supabase with no gate at all. This is
correct and intentional (read-only, page-load-time prefill), not a gap this brief needs to touch.

### Design question 2 — does `demo_meeting_urls` need a new column recording which account saved it?

**Recommended: no, keep this brief scoped to the passcode-mechanism swap only.** Migration `093`'s own
table comment already establishes `demo_meeting_urls` as "Not a partner-facing table" — it was designed
without any per-account identity concept from the start, for a page-level (per-slug) piece of shared
demo-setup state, not a billable/attributable event. B2B-39's own design (migration `100`'s
`demo_dispatches` table comment, quoted above) already establishes that billing/audit attribution
belongs at dispatch time, not save time — nothing in that design implies `demo_meeting_urls` should
also carry identity. Adding a column here would be new scope invented by this brief, not something the
existing design already implies. If Arun wants a "who last touched this slug's meeting details" audit
trail in the future, that is a distinct, separately-scoped ask — not folded in here.

## Known Constraints

- Do not touch `app/api/demo/[slug]/dispatch/route.ts`'s own passcode handling in any way — it is
  already correct today; this brief exists purely to bring the Save action in line with it.
- Do not change the demo page's visible Save / Learn-with-AI flow from the operator's perspective
  beyond what's structurally required to make the passcode field resolve correctly against the new
  mechanism — same fields, same buttons, same page layout.
- Do not add any new schema/column to `demo_meeting_urls` (see Design question 2 above) unless the BA
  finds a concrete reason this brief's own scope requires it — flag rather than silently expanding
  scope if so.
- The GET handler stays exactly as-is — confirmed unauthenticated-by-design, out of scope (see Design
  question 1 above).

## `lib/demo/passcode.ts` / `verifyDemoPasscode()` — dead code question, checked directly

Grepped every call site of `verifyDemoPasscode` in the codebase before concluding anything (not
assumed): it has exactly **one** functional call site anywhere — `app/api/demo/[slug]/meeting/route.ts`
line 71. The other three grep hits are: the function's own definition (`lib/demo/passcode.ts`), a
doc-comment in `dispatch/route.ts` referencing it historically (not a call), and a doc-comment in
`passcode-accounts.ts` referencing it (also not a call). Once this brief swaps the meeting route's POST
handler onto `resolveDemoPasscodeToAccount()`, `verifyDemoPasscode()`, its internal
`timingSafeEqualStrings()` helper, and the `DEMO_MEETING_PASSCODE` env var it reads all become fully
unreferenced in application code — **it can be deleted as part of this brief.** BA should re-confirm
this grep independently at spec time (in case anything changed between tonight and BA dispatch) before
finalizing whether `lib/demo/passcode.ts` is deleted outright or left in place as harmless dead code;
either is acceptable, but if left in place it should be clearly marked as unused/deprecated in a
comment so it isn't mistaken for a still-live mechanism.
